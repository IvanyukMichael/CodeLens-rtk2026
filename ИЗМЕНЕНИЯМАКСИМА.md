## 1. ПРИОРИТЕТ 1 — база ≥80 файлов

**Было:** индексировался только `gymhero` = 47 файлов / 155 чанков (< 80, не проходит ТЗ).
**Стало:** база по умолчанию = **gymhero + corpus_extra + corpus_polyglot = 168 файлов / 1782 чанка**.

### Что добавлено
- **`corpus_extra/`** — снапшоты двух открытых библиотек (атрибуция и лицензии —
  в [corpus_extra/README.md](corpus_extra/README.md)):
  | Подпапка | Источник | Лицензия | Файлов | Чанков |
  |---|---|---|---:|---:|
  | `corpus_extra/click/` | [pallets/click](https://github.com/pallets/click) | BSD-3-Clause | 17 | 591 |
  | `corpus_extra/rich/`  | [Textualize/rich](https://github.com/Textualize/rich) | MIT | 100 | 1017 |
- **`corpus_polyglot/`** — небольшой JS/Java-корпус (см. §2.3, второй язык): 4 файла / 19 чанков.

### Почему именно click + rich
Они **семантически далеки** от домена gymhero (CLI-фреймворк и рендеринг в терминале против
auth / web-API / БД), поэтому их чанки почти не конкурируют с эталонными ответами на
официальные 15 вопросов. Это сознательный выбор, чтобы **не уронить метрику**, добавив при
этом +117 файлов «отвлекающего» кода (честная нагрузка на ретрив 10:1 к целевым чанкам).

### Как сохранена совместимость с метрикой (важно)
- В [index.py](index.py) индексация переведена на **несколько корней**.
  `relative_path` в `chunk_id` считается **от каждого корня по отдельности**, поэтому
  gymhero сохраняет точные `chunk_id` вида `gymhero/...` (калибровка 30/30 не нарушена),
  а доп. корпус получает собственные префиксы `click/…`, `rich/…`, `javascript/…`, `java/…`.
- Проверено программно: **0 коллизий** путей с `gymhero/` и **0 дублей** `chunk_id` между
  корпусами; эталонный `gymhero/security.py:create_access_token:12` присутствует в базе.
- В метаданные каждого чанка добавлены поля **`source`** (gymhero/click/rich/…) и **`lang`**
  (python/javascript/java) — для фильтра в UI и возможной scoped-метрики.

### Изменения в index.py
- `python index.py` (без аргументов) → строит **всю базу** (`DEFAULT_ROOTS`).
- `python index.py <папка> [<папка2> …]` → индексирует только указанные корни (back-compat,
  напр. `python index.py gymhero` — только официальный корпус).
- Новые функции `collect_chunks(roots)` (слияние чанков из всех корней, Python через AST +
  JS/Java через tree-sitter, дедуп по `chunk_id`) и `_source_of(path)`.

### Метрика — текущий статус (честно)

**Исходная база (только gymhero, 155 чанков) ЦЕЛА и метрика не пострадала:**
`python score.py --predictions results.json --questions eval_questions.json` →
**Total P@5 = 0.800** (перепроверено сейчас). Текущий `chroma_db/` всё ещё содержит
рабочую коллекцию на 155 чанков — продукт запускается и ищет как прежде.

**Расширенную базу (168 файлов / 1782 чанка) на этой CPU-машине собрать не удалось:**
полный эмбеддинг занял бы 11+ часов (см. §0). Прогон был остановлен по просьбе. Поэтому
**P@5 на расширенной базе ещё НЕ измерен** — это надо сделать на машине с GPU:

```
python index.py            # пересобрать всю базу (на GPU — минуты)
python predict.py          # пересобрать results.json
python score.py --predictions results.json --questions eval_questions.json
```

Что уже **проверено на расширенной базе без эмбеддинга** (быстрые, детерминированные
шаги): извлечение даёт 168 файлов / 1782 чанка; **0 коллизий** путей с `gymhero/` и
**0 дублей** chunk_id; эталонные chunk_id gymhero на месте; `enrich.py` собирает текст
для всех 1782 чанков. То есть формат и совместимость с метрикой гарантированы — открытым
остаётся только эмпирический вопрос «не вытесняют ли distractor-чанки правильные ответы из
top-5», ответ на который даст один GPU-прогон `score.py`. Ожидание — 0.800 удержится
(click/rich домен-далёкие); если просядет — откат к scoped-варианту (фильтр официальной
выдачи по `source == "gymhero"`), как договаривались.

## 2. ПРИОРИТЕТ 2 — бонусы

### 2.1 LLM-чат (3-я вкладка)
- Новый модуль **[chat.py](chat.py)**: берёт top-N фрагментов из `search.search()`, отдаёт их
  локальной LLM (Ollama `qwen2.5-coder:7b`) и собирает связный ответ **строго по найденному
  коду** со ссылками `path:name`. Анти-галлюцинация: если ответа в коде нет — модель обязана
  это сказать. Стриминг ответа (`ollama_chat_stream`) + нестриминговый `ollama_chat`.
  Переиспользует адрес/модель Ollama из `hyde.py` (один источник правды).
- В **[app.py](app.py)** добавлена вкладка **💬 Ответ (LLM)** между Поиском и Метриками:
  ввод вопроса → поиск фрагментов → (если Ollama доступна) стриминг ответа → раскрывающийся
  список источников с подсветкой. **Graceful fallback:** без Ollama показываются только
  фрагменты + предупреждение. Порог «не найдено» применяется и здесь.
- CLI для быстрой проверки: `python chat.py "как создаётся токен доступа"`.

### 2.2 Docker Compose
- **[Dockerfile](Dockerfile)** — образ продукта (python:3.12-slim, CPU-torch).
- **[docker-compose.yml](docker-compose.yml)** — сервис `codelens` (Streamlit на 8501) +
  опциональный сервис `ollama` (для HyDE/чата). Тома: кэш моделей HF (bge-m3 ~2.3 ГБ переживает
  пересборку), персистентная `chroma_db`, модели Ollama.
- **[docker/entrypoint.sh](docker/entrypoint.sh)** — при старте строит базу (`python index.py`,
  если её нет) и поднимает Streamlit. LF-окончания зафиксированы через корневой `.gitattributes`.
- **[requirements-docker.txt](requirements-docker.txt)** — CPU-сборка torch + те же пины.
- **[.dockerignore](.dockerignore)** — без `.git`, `__pycache__`, `chroma_db`; `cache/` оставлен
  (нужен для офлайн-HyDE).
- Запуск: `docker compose up --build` → http://localhost:8501. LLM-модель в Ollama-контейнере
  подтянуть отдельно: `docker compose exec ollama ollama pull qwen2.5-coder:7b`.
- **Не ломает запуск двумя командами** — это альтернативный путь, локальный `python index.py`
  + `streamlit run app.py` остаётся основным.
- ⚠️ Здесь Docker не установлен, поэтому образ **не собирался локально** — конфигурация
  написана по конвенции, требует сборки на машине с Docker.

### 2.3 Второй язык — JavaScript и Java (tree-sitter)
- Новый экстрактор **[extract_chunks_ts.py](extract_chunks_ts.py)**: парсит `.js/.jsx/.mjs` и
  `.java` через tree-sitter и выдаёт чанки **той же схемы**, что питоновский экстрактор
  (`chunk_id = path:name:line`, методы как `Class.method`, сигнатура = строка объявления,
  docstring = JSDoc/Javadoc). Поэтому они проходят через общий `enrich.py` и ложатся в ту же
  коллекцию ChromaDB — поиск работает по трём языкам единообразно.
- Грамматики — прекомпилированные wheel-пакеты (компилятор C не нужен). Если tree-sitter не
  установлен — экстрактор возвращает `[]` (питоновский путь продукта не ломается).
- Демо-корпус **`corpus_polyglot/`**: `javascript/auth.js`, `javascript/userController.js`,
  `java/UserService.java`, `java/AuthController.java` (свой код, без лицензионных вопросов) —
  4 файла, 19 чанков (классы, конструкторы, методы, функции).
- Подключён в `index.py` (входит в `DEFAULT_ROOTS`), метаданное `lang` различает языки.

### 2.4 Кэш эмбеддингов в index.py (производительность)
- В `index.py` добавлен кэш `cache/index_embeddings.pkl`: ключ — `sha1(enriched_text)`,
  значение — вектор bge-m3. При повторной сборке неизменные чанки берутся из кэша,
  пересчитываются только новые/изменённые; если изменений нет — модель **вообще не грузится**.
  На CPU это превращает многочасовую пересборку в секунды (после первого полного прогона на GPU).
- ⚠️ Кэш сейчас **пуст** — полный прогон, который должен был его наполнить, был прерван.
  Первый успешный `python index.py` (лучше на GPU) наполнит кэш; последующие сборки будут мгновенными.

## ПРИОРИТЕТ 3 (пункт 1) — расширение eval до 170 вопросов

**Было:** extended 56 / combined 71. **Стало:** **extended 155 / combined 170**
(15 официальных + 155 наших). Исходные 56 (`g_01..g_56`) сохранены без изменений.

### Как сделано (методология честно)
- Ollama (которой пользуется `gen_eval.py`) **не установлена**, поэтому автором новых вопросов
  выступил **Claude** — по тем же промтам/правилам и **с теми же детекторами качества** из
  `gen_eval.py`. Это методологический эквивалент (сильнее по модели); в отчёте помечается как
  «LLM-generated + detector-validated».
- Новый модуль **[gen_eval_llm.py](gen_eval_llm.py)** (2 шага): `worktable` отбирает чанки-кандидаты
  gymhero (как `gen_eval`) и планирует пары (chunk, язык) до цели ~155; затем автор заполняет
  `eval/_authored.json`; `assemble` прогоняет каждый вопрос через детекторы
  `leaks_name` (утечка имени) и `too_similar` (копирование few-shot), собирает
  `eval/eval_extended.json` и пересобирает `eval/eval_combined.json`.
- В gymhero всего **104 чанка-кандидата** (155 − 27 эталонных − короткие/дандеры). Чтобы дойти
  до 155, часть чанков получила вопрос на ОБОИХ языках (ru+en) — это полезно для кросс-языкового среза.

### Результат (проверено)
- **155 extended / 170 combined**; 0 битых `chunk_id`, 0 дублей `question_id`, все поля на месте,
  пустых вопросов нет, все 99 новых прошли детекторы.
- Баланс: ru 74 / en 81; easy 18 / medium 117 / hard 20; категории api/db/validation/auth/config/business_logic.

### Что осталось (не блокирует расширение)
- HyDE-кэш покрывает только старые запросы. Для 99 новых вопросов живой HyDE на странице Метрик
  потребует Ollama (иначе graceful fallback без HyDE на этих вопросах). Официальный `predict.py`
  (только 15) не затронут.
- Пере-анализ значимости HyDE на 170 (`ablation_full.py`) требует HyDE-генераций для новых вопросов
  (Ollama) — отдельный шаг Приоритета 3.
