## 2. Жёсткие факты о данных (ВЕРИФИЦИРОВАНО, не пересматривать)

### 2.1 Формат chunk_id
```
{relative_path}:{name}:{start_line}
```
- `relative_path` — от **корня репозитория** (внешняя папка `gymhero/`), прямые слэши `/`.
  Пример: `gymhero/api/dependencies.py` (внутренний пакет тоже называется `gymhero`).
- `name` — имя функции/класса. **Для метода — `ClassName.method_name`** (квалифицированное).
- `start_line` — `node.lineno` из `ast` (строка `def`/`class`, без декораторов).

### 2.2 Как считается метрика (`score.py`)
- `Precision@5 = matched / min(5, len(correct))` на каждый вопрос; mean по 15 вопросам.
- Сравнение chunk_id: `path` и `name` — **точное, case-sensitive**; `start_line` — **±2 строки**.
- Дубликаты в топ-5 не засчитываются повторно.
- Формат предсказаний — `results.json`: массив из 15 объектов `{question_id, top_5_chunks[5]}`.

### 2.3 Калибровка пройдена
Рекурсивный экстрактор (см. §3) даёт **дельту 0 строк на всех 30 эталонных chunk_id** из
`eval_questions.json`. То есть формат гарантированно совместим. Не «улучшать» логику имён/строк.

### 2.4 Размер базы
gymhero = **47 `.py` файлов, 155 чанков**. Для «≥80 файлов» и для глубины исследования
**обязательно добавить открытые Python-репозитории** (см. §7).

### 2.5 ⚠️ Ловушка в README организаторов
Их пример `extract_chunks` через `ast.walk(tree)` **эмитит методы дважды**: один раз как
`ClassName.method` (внутри ветки ClassDef), второй — как голое `method` (когда `walk` дойдёт
до узла метода и попадёт в `elif FunctionDef`). А «минимальный workflow» вообще пишет методам
голое имя без класса. **Использовать только корректный экстрактор из §3.**

## 3. Корректный AST-экстрактор (эталон)

```python
import ast
from pathlib import Path

def extract_chunks(py_file: Path, repo_root: Path) -> list[dict]:
    """Возвращает список чанков {chunk_id, path, name, kind, start, end, code, docstring}."""
    rel = py_file.relative_to(repo_root).as_posix()
    src = py_file.read_text(encoding="utf-8", errors="replace")
    try:
        tree = ast.parse(src)
    except SyntaxError:
        return []
    lines = src.splitlines()
    out = []

    def emit(node, qualname, kind):
        start = node.lineno                      # 1-based, строка def/class (как в эталоне)
        end = getattr(node, "end_lineno", start)
        code = "\n".join(lines[start - 1:end])
        out.append({
            "chunk_id": f"{rel}:{qualname}:{start}",
            "path": rel, "name": qualname, "kind": kind,
            "start": start, "end": end, "code": code,
            "docstring": ast.get_docstring(node) or "",
        })

    def walk(node, prefix=""):
        for child in ast.iter_child_nodes(node):
            if isinstance(child, ast.ClassDef):
                emit(child, prefix + child.name, "class")
                walk(child, prefix + child.name + ".")     # методы получают ClassName.
            elif isinstance(child, (ast.FunctionDef, ast.AsyncFunctionDef)):
                emit(child, prefix + child.name, "function")
                # не спускаемся во вложенные функции — они редко являются эталонами
    walk(tree)
    return out
```

Ключевое: `iter_child_nodes` + ручная рекурсия (а не `ast.walk`), префикс класса для методов,
`node.lineno` для строки. Это и есть «дельта 0».

## 4. Целевая архитектура (что строим)

```
ИНДЕКСАЦИЯ (index.py <папка>):
  обход .py → extract_chunks() → ENRICH(текст чанка) → embed() → сохранить в FAISS + ChromaDB
                                                                  + BM25-индекс (для гибрида)

ПОИСК (по запросу):
  query → [опц. HyDE: LLM генерит гипотетический код] → embed
        → ВЕКТОР top-N (N≈30..50)  ┐
        → BM25   top-N             ┼─ RRF (reciprocal rank fusion, настраиваемый вес)
                                   ┘
        → CROSS-ENCODER rerank top-N → top-5
        → (опц.) LLM собирает связный ответ из найденных фрагментов
```

### 4.1 Enrichment чанка (самый дешёвый буст метрики)
Эмбеддить НЕ голый код, а обогащённый текст. Кандидаты на включение в эмбеддинг-текст:
- путь файла + имя класса-родителя (контекст «где это»);
- сигнатура (имя, аргументы, тип возврата);
- docstring;
- **опц. NL-summary**: одна фраза от локального LLM «что делает эта функция» — мощно
  закрывает разрыв «вопрос на естественном языке ↔ имена в коде». Кэшировать на диск.

Это прямой ответ на боль из ТЗ («слова вопроса не совпадают с именами функций»).

### 4.2 Стратегия чанкинга — обоснование для защиты (заготовить!)
> «Чанк = одна функция/класс/метод, потому что это минимальная самостоятельная семантическая
> единица Python-кода: у неё есть имя, сигнатура и docstring, она индексируется AST детерминированно
> и совпадает с гранулярностью, в которой разработчик задаёт вопрос («где проверяется суперпользователь»).
> Крупные функции мы дополнительно обогащаем сигнатурой и summary; файловую гранулярность отвергли —
> она смешивает несколько ответственностей в один вектор и роняет precision.»

Подкрепить **экспериментом**: сравнить минимум 2-3 стратегии чанкинга (function-level vs
function+enrichment vs file-level vs sliding-window для длинных функций) по P@5 — таблица в отчёте.

## 5. Что реально двигает метрику (порядок приоритетов)

Ожидаемый вклад (проверить ablation, не верить на слово):
1. **Модель эмбеддингов** — база всего. Мультиязычная + код-aware.
2. **Enrichment + NL-summary** — закрывает кросс-языковой и NL↔code разрыв.
3. **Cross-encoder reranking** — обычно +большой precision на top-5.
4. **HyDE** — заметно тянет слабые/локальные модели (на 1 этапе ~+25%).
5. **Гибрид (BM25+вектор, RRF)** — помогает точным совпадениям имён/терминов.

### Модели-кандидаты (под 12 ГБ RTX 4080 mobile)
Локальные эмбеддинги: `BAAI/bge-m3`, `intfloat/multilingual-e5-large`,
`jinaai/jina-embeddings-v2-base-code`, `Alibaba-NLP/gte-Qwen2-1.5B-instruct` (уже знаком по 1 этапу),
`ai-forever/FRIDA` (силён на русском).
Reranker: `BAAI/bge-reranker-v2-m3` (или `jinaai/jina-reranker-v2`).
API (для «лидер-сравнения», опц., через триал-ключи): Cohere `embed-v4`, Voyage `voyage-code-3`.
HyDE/ответы (локально): Ollama `qwen2.5-coder:7b` или `mistral:7b` (q4 влезает).

> Финальный продукт может работать на лучшей **локальной** конфигурации (воспроизводимо без API),
> а в отчёте показать, что API-модель (если тестировали) — потолок. Так делал победитель.

## 6. Метрики и эксперименты (исследовательский слой)

### 6.1 Считать не только P@5
- **Precision@5** (основная, их `score.py`).
- **Recall@3, Recall@5, MRR, nDCG@5** — для отчёта.
- **Latency**: p50/p95 на 10+ последовательных запросах (требование ТЗ).

### 6.2 Срезы
- по языку (ru / en) — кросс-языковой анализ;
- по сложности (easy / medium / hard);
- по категории (auth, api, db, validation, config, errors, business_logic).

### 6.3 Ablation-матрица (главная таблица отчёта)
Прогнать сеткой: `модель × стратегия_чанкинга × {HyDE on/off} × {hybrid on/off} × {rerank on/off}`.
Сделать **единый harness** `eval_runner.py`, который читает конфиг, гоняет матрицу, пишет
`results/*.json` + сводный `report.csv` + markdown-таблицу. Жюри это любит: воспроизводимо и наглядно.

### 6.4 «Негативные» запросы
В `sample_queries.txt` намеренно есть 3 запроса про отсутствующую функциональность
(blockchain/WebSocket/rate limiting). Хорошая система должна показывать **низкую релевантность**
и честно говорить «не найдено». Реализовать порог уверенности и показать это на демо — сильный ход.
